# Переплёт · Book Store

Локальный книжный магазин на Java 21, Spring Boot, Maven, PostgreSQL и Liquibase.
Каталог, профиль и аватарка, корзина, избранное, отзывы, цены, склад, заказы и история покупок.
Адрес приложения: **http://localhost:8080/**.

## Обновление и запуск в IntelliJ IDEA

1. Получите изменения в `master` через Git → Pull. Перезагрузите Maven-проект.
2. Используйте JDK 21 в Project SDK и Maven Runner.
3. В Run → Edit Configurations → BookStoreDemoApplication → Environment variables
   задайте `DB_PASSWORD` с вашим паролем PostgreSQL. По умолчанию база `BOOKS`,
   пользователь `postgres`. При необходимости переопределите `DB_URL` и `DB_USERNAME`.
4. Запустите `BookStoreDemoApplication`. Liquibase добавит новые таблицы и поля.
5. Откройте http://localhost:8080/ и войдите в аккаунт.

Приложение привязано к 127.0.0.1:8080. Переопределения: `SERVER_ADDRESS` и `PORT`.
Пароли базы и администратора не записывайте в исходники и не публикуйте в Git.

Для запуска без PostgreSQL укажите Active profiles: `local`. Он использует отдельную
файловую H2 в `data/bookstore.mv.db`. Сохраняйте каталог `data/`: это ваши локальные
данные. Переключение между PostgreSQL и H2 не переносит записи автоматически.

```sh
./mvnw spring-boot:run
# Или без PostgreSQL:
./mvnw spring-boot:run -Dspring-boot.run.profiles=local
```

Windows: `mvnw.cmd`. Для запуска собранного JAR: `java -jar target/book-store-0.0.1-SNAPSHOT.jar`.

## Как получить права администратора

Все существующие пользователи и новые регистрации получают роль `CUSTOMER`.
Публичная регистрация не позволяет назначить себе роль администратора.

Чтобы назначить администратором **свой существующий аккаунт**, добавьте в Environment variables:

```text
BOOKSTORE_ADMIN_EMAIL=ваша_почта
```

Перезапустите приложение, выйдите из аккаунта и войдите снова. Пароль аккаунта не изменится.
В профиле появится кнопка **Управление магазином**, внизу каталога — **Добавить книгу в каталог**.

Для создания совершенно нового администратора задайте также `BOOKSTORE_ADMIN_PASSWORD`
(от 8 символов, максимум 72 байта UTF-8). Пароля по умолчанию нет. После создания
можно удалить обе переменные из конфигурации запуска: роль сохранена в базе.
Настройка не отзывает права ранее назначенных администраторов.

## Работа со складом и ценами

В профиле администратора откройте **Управление магазином**:

1. Найдите и выберите книгу.
2. Отредактируйте название, автора, раздел и цену в рублях. Нажмите **Сохранить карточку**.
3. В блоке **Поступление на склад** укажите количество и основание, например номер
   накладной. Нажмите **Зарегистрировать поступление**.
4. В **Истории склада** видны время, сотрудник, книга, приход/резерв/снятие резерва/отправка,
   изменение количества, остатки после операции и связь с заказом.

После обновления у прежних книг цена не задана, физический остаток равен нулю.
Миграция не придумывает реальные цены и поставки. Уже существующая корзина и избранное
сохраняются, но заказ можно оформить только после назначения цены и поступления книг.
Новая книга также создаётся без цены и остатка; затем настройте её в панели.
Все суммы хранятся в DECIMAL/BigDecimal, валюта — RUB. Онлайн-оплата не подключена.

## Заказы и история покупок

Покупатель добавляет книги в корзину и нажимает **Оформить заказ**. Сервер проверяет
цены и остатки, сохраняет названия, авторов и цены на момент заказа, резервирует книги
и очищает корзину. Все действия выполняются одной транзакцией. Если хотя бы одной
позиции не хватает, заказ не создаётся, корзина и остатки сохраняются.

Статусы идут последовательно:

`CREATED → CONFIRMED → PACKED → SHIPPED → COMPLETED`

В интерфейсе: Создан → Подтверждён → Собран → Отправлен → Завершён.
Администратор меняет их через **Все заказы → Состав и история**.
Покупатель видит только собственные заказы в профиле через **Мои заказы**.
Завершённые заказы образуют историю покупок. История сохраняет автора и время каждого перехода.

Покупатель может отменить свой заказ до отправки; администратор — любой заказ до отправки.
Отмена переводит заказ в `CANCELLED` и освобождает резерв. При отправке уменьшаются и
физический остаток, и резерв. Повторный запрос того же статуса не списывает книги снова.
Отправленный заказ отменить нельзя: возвраты требуют отдельного процесса и пока не реализованы.
Резерв не истекает автоматически; администратор должен обработать или отменить заказ.

Оформление и поступление принимают UUID `requestKey`: повтор того же запроса не создаёт
дубликат. Браузер сохраняет ключ повтора до подтверждённого успеха. Цена в ранее созданном
заказе не изменяется при редактировании каталога. Блокировки книг берутся в порядке ID,
поэтому два покупателя не могут зарезервировать один последний экземпляр.

## Таблицы и просмотр в IDEA

| Таблица | Содержимое |
|---|---|
| `books` | Каталог, цена, физический остаток `stock`, резерв `reserved` |
| `store_users` | Аккаунты и роли CUSTOMER/ADMIN |
| `cart_items` | Текущая корзина, количество, added_at и updated_at |
| `cart_details` (VIEW) | Корзина с именем, почтой, названием, автором, ценой и датами |
| `store_orders` | Заказы, владелец, сумма, валюта, статус и даты |
| `order_items` | Снимок состава и цены каждого заказа |
| `order_events` | История статусов и кто их менял |
| `stock_movements` | Поступления, резервы, отмены и отправки |
| `user_favorites`, `book_reviews` | Избранное и отзывы |

Для читаемой корзины в Query Console выполните:

```sql
SELECT * FROM cart_details ORDER BY email, book_title;
```

У старых строк корзины `added_at` и `updated_at` останутся NULL до соответствующих
новых действий: точное время прежних добавлений неизвестно. При новом добавлении
заполняются обе даты; изменение количества обновляет только `updated_at`.

## Архитектура и доступ

Контроллеры отвечают за HTTP и валидацию, сервисы — за бизнес-правила и транзакции,
репозитории — за JPA/JDBC. DTO отделены от сущностей. `OrderStatus` задаёт допустимые
переходы. `OrderService` сохраняет снимки заказа и управляет резервами через блокировки
строк книг; `InventoryService` регистрирует поступления и правит карточки. В базе есть
ограничения на цены, количество, роли, остатки и уникальные ключи повторных запросов.

Spring Security защищает `/api/admin/**` и создание книг ролью ADMIN; клиентские кнопки
не являются механизмом защиты. Сервисы также проверяют администратора и владельца заказа.
Изменения требуют CSRF. Регистрация всегда создаёт CUSTOMER. Пароли хранятся как BCrypt-хеши.
Аватарки нормализуются в PNG 256×256; исходник — PNG/JPEG до 2 МБ и 4096×4096.

`api-client.js` обрабатывает HTTP/CSRF; `app.js` — каталог, профиль и личный выбор;
`commerce.js` — административную панель, оформление и историю заказов.
Старые миграции не переписаны; новые изменения находятся в `commerce.xml`.
Адаптер `LowercaseH2Database` согласует регистр имён Liquibase с существующей локальной H2.

Основные новые маршруты:

- `GET/POST /api/orders`, `GET /api/orders/{id}`, `POST /api/orders/{id}/cancel`.
- `GET /api/admin/orders`, `PUT /api/admin/orders/{id}/status` с `{"status":"CONFIRMED"}`.
- `GET /api/admin/inventory`, `PUT /api/admin/books/{id}` с name, author, category, price.
- `POST /api/admin/books/{id}/receipts` с quantity, note, requestKey.
- `GET /api/admin/stock-movements`.

Списки заказов и движений выдаются по 50 строк, параметр `page` начинается с 0.
Каталог пока загружается целиком; поиск и страницы по 12 книг работают в браузере.
Гостевые корзина и избранное хранятся отдельно и не переносятся автоматически в аккаунт.

## Проверка

```sh
# JDK 21 и Docker для PostgreSQL Testcontainers
./mvnw clean verify
# H2 без Docker
./mvnw -Dtest=BookMapperTest,ProfileControllerTest,CatalogTest,SelectionTest,MutationSafetyTest,CommerceTest test
```

Тесты проверяют права, запрет подмены роли, точность суммы и снимок цен, изоляцию заказов,
переходы статусов, отмену, идемпотентность, аудит, даты корзины и конкурентную покупку
последнего экземпляра на H2 и PostgreSQL. GitHub Actions также запускает реальный JAR
и Chromium: администратор задаёт цену и приход, покупатель оформляет заказ, сервер
перезапускается на той же H2, заказ отменяется, следующий проходит до завершения.
Снимки экрана и логи находятся в артефакте `test-report`.

### Оформление заказа и письмо покупателю

Кнопка «Оформить заказ» активна для вошедшего покупателя с непустой корзиной.
Администратор задаёт любую цену от 0,01 до 99 999 999,99 руб. в «Управлении магазином»
и оформляет поступление книг. При отсутствии цены или нехватке остатка сервер
объясняет причину и сохраняет корзину. Цена берётся из каталога на момент оформления,
а затем сохраняется в заказе; покупатель не может подменить цену запросом из браузера.

При создании заказа в той же транзакции создаётся запись `order_mail`.
Письмо отправляется на адрес покупателя из заказа и содержит номер, дату (МСК),
названия и авторов, количество, цены и итог. Оформление в стиле «Переплёта»:
тёмно-зелёная шапка, светлый фон, подпись магазина. Есть и текстовая версия письма.
Это уведомление о создании заказа, не оплата и не кассовый чек.

Для реальной отправки из localhost добавьте в IDEA → Run → Edit Configurations →
Environment variables (сохранив DB_PASSWORD и BOOKSTORE_ADMIN_EMAIL):

| Переменная | Значение |
|---|---|
| BOOKSTORE_MAIL_ENABLED | true |
| MAIL_HOST | SMTP-сервер вашего почтового сервиса |
| MAIL_PORT | 587 для STARTTLS либо 465 для TLS |
| MAIL_USERNAME | Логин почтового ящика отправителя |
| MAIL_PASSWORD | Пароль приложения для SMTP, выданный почтовым сервисом |
| MAIL_FROM | Адрес отправителя, разрешённый этим сервисом |
| MAIL_STARTTLS | true для 587; false для 465 |
| MAIL_SSL | false для 587; true для 465 |

Перезапустите приложение после изменения настроек. Секреты не добавляйте в код,
коммиты или скриншоты. Параметры сервера уточняйте у своего почтового провайдера.
Для получения письма на свою почту оформите заказ из аккаунта с этим адресом.

Без настройки SMTP заказы работают; письма ожидают в базе. После включения отправки
накопленные уведомления будут отправлены. Проверка очереди каждые 15 секунд,
повторная попытка при ошибке через 10 минут, пока приложение запущено.
Статус виден в деталях заказа, кнопка «Обновить статус письма» перечитывает его.
«Передано почтовому серверу» не гарантирует попадания во входящие: проверьте «Спам».
Повтор оформления с тем же ключом не создаёт второе письмо. При аварии процесса
после принятия письма SMTP, но до отметки в БД, повторная доставка возможна
(семантика at-least-once). Старые заказы до этой миграции не рассылаются.

### Номера заказов

Покупатели и администраторы видят единый номер вида `000001` в списке заказов,
деталях, истории склада, теме и тексте письма. База присваивает уникальный числовой
номер автоматически, включая уже существующие заказы при миграции. После `999999`
номер расширяется до семи цифр. Пропуски в нумерации при отмене транзакций допустимы;
номера не переиспользуются. UUID остаётся внутренним идентификатором API, права
доступа к заказам по-прежнему проверяются. Уже доставленные письма не изменяются.
